## Reviewer JrJk（Rating 6, Confidence 3）

### JrJk-C1
> **Comment:** The reliability of the gold tables needs more validation. The pipeline reverse-engineers rendering code from chart images using an LLM, then extracts the underlying data from that code. But the paper reports no fidelity metrics for this reconstruction step. ... This matters most for Task 2, which requires precise numerical computation.

**Response:** We appreciate this concern and would like to clarify a key design point that may not have been clearly articulated previously, which directly addresses concerns about the reliability of the gold tables. **The charts ultimately used for evaluation are not the original images from reports, but charts rendered from rendering code; and the gold-table is directly extracted from the underlying data in that same code.** That is, the charts seen by the model and the data serving as the ground truth **originate from the same code**, and the two are necessarily consistent by construction—there is no环节 where "values are first inferred from images by an LLM" that would introduce reading errors. Therefore, the fidelity issue in the sense of "whether reconstructed data matches values in the images" does not naturally exist in our pipeline, nor do we need to post-hoc verify chart-data consistency using metrics such as match rate or rejection rate.

A separate layer of consistency to distinguish is **the degree of visual fidelity of rendered charts relative to original report charts** (data distribution, numerical magnitudes, trend trajectories). This layer is ensured by human supervision and iterative adjustment, as stated in main §2.2: "iterative human feedback to ensure that the generated charts faithfully preserve the original content and visual patterns." This concerns the realism of the benchmark but does not affect "whether the chart and gold-table are consistent." Furthermore, for Task 2 which the reviewer is particularly concerned about, appendix G also specifies that we convert rationales into executable Python code to compute final labels ("use variables to replace the intermediate calculation results... as the code execution is more accurate and avoids cumulative errors"), further ensuring the accuracy of numerical computation. If the reviewer considers it beneficial, we are also happy to supplement a more detailed description of the manual verification process for "visual consistency between rendered charts and original reports" in the revised version.

### JrJk-C2
> **Comment:** Tasks 3 and 4 rely heavily on automatic synthesis by a frontier reasoning model, followed by human correction. The paper ... does not report the proportion of items corrected, what types of corrections were made, or inter-annotator agreement.

**Response:** We thank the reviewer for their attention to the rigor of Task 3/4 data construction, which is indeed crucial to the credibility of the benchmark. We take this opportunity to clarify the process more thoroughly.

**Regarding the rationale for using a text-only reasoning model for synthesis.** We first explain the basis for this choice. As shown in main §2.2 and Figure 2 (The Construction Pipeline of MultiChartQA-R, which intuitively demonstrates the complete pipeline: chart-code pair collection → question-answer pair construction → multilingual expansion), the synthesis of Tasks 3/4 does not allow the model to "create questions out of thin air," but rather takes **chart-rendering code containing underlying gold-table information together with task definitions** as input, provided in a few-shot manner to a frontier reasoning model to generate questions, correct options, and explanations of why they are correct, and then generate distractors and explanations of why they are wrong ("we use chart-rendering code, which contains the underlying gold-table information, together with task definitions as input to a frontier reasoning model in a few-shot manner to generate questions, correct options, and explanations"). That is, the model's generation is **grounded in deterministic structured data (gold-table)**—its role is closer to "organizing reasoning questions conforming to task definitions on given ground-truth data" rather than freely fabricating content; we also "incorporate web-retrieved knowledge during generation" to enhance domain relevance. Precisely because the entire synthesis process is anchored to the verifiable factual source of the gold-table, using a text-only reasoning model to undertake this high-cost cross-chart reasoning annotation is both efficient and ensures strict correspondence between questions and ground-truth data; this is also why we use manual annotation for Task 1 (which is straightforward) and "automatic synthesis + human revision" for Tasks 3/4 (which have high annotation costs).

**Regarding potential circular risk.** There is another design detail we may not have clearly articulated previously: the model used to synthesize Tasks 3/4 questions is a **text-only reasoning model** that only accesses structured textual information (gold-table content, rationales, etc.) during generation and does not "look at charts"; whereas the actual evaluation targets of the benchmark are **Multimodal Large Language Models (MLLMs)** that need to perceive and integrate visual information from chart images to answer. Since the two differ in both modality (text-only vs. multimodal) and model identity, it is difficult for the evaluated model to achieve high scores merely by "aligning with the synthesis model's textual logic"—the cross-chart visual reasoning it actually faces is precisely what the synthesis model has never experienced. Therefore, this differs from the self-preference scenario where "the same model both synthesizes and answers." We also observe phenomena consistent with this in experiments: existing strong models (including multimodal models used as baselines) do not show systematic advantages on Tasks 3/4 (see appendix Table 5), indirectly corroborating this point. We will clarify this distinction—"text-only model for synthesis, multimodal model for evaluation"—more explicitly in the revised version to address related concerns.

**Regarding statistics on modification proportion and modification types.** We fully understand the reviewer's desire to know the extent of human intervention—a natural concern when assessing data quality. Here we would like to share our consideration: the goal of human revision is to ensure the quality of **final released instances**, and all instances that ultimately enter the benchmark are "human-refined benchmark instances rather than raw model outputs" (main §2.2). That is, regardless of whether a question undergoes substantial rewriting or only minor adjustments, it must pass unified quality standards before being included. The reliability of the benchmark primarily depends on the quality of the final product, for which there is already relatively direct evidence: appendix B.1 specifies that human revision covers four aspects (Question-type alignment, Validity of correct options, Effectiveness of distractors, Explanation consistency), and a 30% sampled Post Hoc Quality Audit shows "Task 3 achieved an average score of 9.1/10 with an inter-rater agreement of 85%, while Task 4 achieved an average score of 9.3/10 with an inter-rater agreement of 87%." Considering that "proportion of significant modifications" itself is difficult to define with a unified criterion, and that this proportion alone does not necessarily reflect the quality of the final product, we prefer to supplement a **qualitative description and typical examples of modification types** in the appendix (i.e., common revision scenarios for each of the four aspects mentioned above), to make the process more transparent and understandable. Of course, if the reviewer considers that providing a quantified modification proportion would be more helpful, we would be happy to supplement it accordingly and welcome further guidance on the desired statistical criterion.

### JrJk-C3
> **Comment:** On evaluation design, the weight settings for easy and hard errors in the MFβ metric feel somewhat arbitrary. ... It also does not test whether model rankings shift under alternative settings.

**Response:** We thank the reviewer for their careful consideration of the evaluation design. The reasonableness of the weights and the stability of rankings are indeed critical to whether MFβ is convincing. We provide detailed explanations from two perspectives: "why the weights are set this way" and "whether rankings change with weights."

**(1) The weights are not arbitrarily set, but are predetermined by the benchmark's annotation design.** As stated in appendix D.2 (Design Rationale), the fixed weights are "determined from the benchmark's annotation design before model-level analysis, rather than tuned to maximize any particular model ranking"—that is, `w_e` and `w_h` are determined **before** any model-level analysis, based on the risk structure of the data itself, rather than tuned post-hoc to make a particular model rank well. The underlying intuition is that hard errors (contradicting chart evidence, involving seemingly rigorous but incorrect reasoning, or hallucination-type errors) are more harmful than easy errors (approximate errors that clearly do not use chart data or have obviously wrong conclusions), and therefore deserve heavier penalties, so we set `w_e=1.0` and `w_h=0.5`. The formal definition is provided in appendix D.3 (Eqs. 5–9), and the semantics of β are given in D.4: "When β=1, the metric balances precision and recall equally. When β>1, greater emphasis is placed on avoiding incorrect selections... When β<1, greater emphasis is placed on covering correct options."

**(2) The influence of β has already been systematically explored in the original paper's appendix.** Appendix D.5 plots MFβ curves for all models across different β values in **Figure 5 / Figure 6**, and analyzes the guiding significance of curve intersection points for "scenario-based model selection" (recall-oriented and precision-oriented tasks can select different models based on intersection point positions), while using InternVL2-26B as an example to note that some models are relatively sensitive to β. That is, the behavior of the β dimension has already been characterized previously and is not untested.

**(3) Regarding the reviewer's concern about "whether rankings change with weights," we have supplemented a dedicated weight sensitivity experiment for verification.** Using the paper's configuration `w_e=1.0, w_h=0.5` as the baseline, we swept **9 weight configurations** across all **16 models and 3 languages** (fixing hard=0.5 while varying easy ∈ {0.5, 0.75, 1.0, 1.25, 1.5}; fixing easy=1.0 while varying hard ∈ {0, 0.25, 0.5, 0.75, 1.0}), recomputing MFβ and rankings for each configuration and comparing against the baseline. The results show highly robust rankings:
- **Top-1 is consistently claude-sonnet-4 across all 9 configurations and 3 languages, without exception**;
- **The Top-3 set is almost entirely unchanged** (only under the most extreme configuration do Qwen3-VL-32B and gemini-2.5-pro swap 3rd place);
- The maximum absolute rank shift is only 0–1 under most configurations, and even the most extreme `e0.5_h0.5` reaches only 3 in en (max 1 in cn, max 2 in es).

Weight changes mainly cause an overall shift in absolute scores (e.g., increasing hard penalties causes more pronounced score drops for "high-recall but high-false-positive" models), but do not change the relative superiority judgment among models. This demonstrates that the chosen `w_e=1.0, w_h=0.5` is not a "special" point, but falls within a **stable ranking plateau**.

**(4) We also note that this is only a "balanced" default setting, and the framework natively supports scenario-based adjustment.** For high-risk/high-compliance scenarios (e.g., medical, financial decision-making), β can be increased to more heavily penalize incorrect selections and favor precision; for exploratory/recall-priority scenarios, β can be decreased; for different judgments on the harm of the two error types, `w_e` and `w_h` can be adjusted accordingly. The sensitivity experiment precisely shows that model relative rankings remain stable within this adjustable range, so users can confidently reset weights according to their own risk preferences. Detailed experimental data can be found in [`supplementary_experiments.md`](./supplementary_experiments.md), and we will include the above sensitivity analysis table and explanation in the revised appendix.

### JrJk-C4
> **Comment:** The paper attributes the noise robustness of proprietary models to "superior intrinsic relevance assessment," but does not dig into where this capability gap comes from. Is it model scale, training data, or architecture?

**Response:** We thank the reviewer for this very insightful comment. We agree that the original phrasing "superior intrinsic relevance assessment" is overly causal and somewhat vague, and should be revised to more restrained, observation-based表述. Meanwhile, several analyses already in the paper can help **preliminarily localize which环节 this capability gap more likely falls into**, which we summarize below as a substantive response to the reviewer's question.

**(1) The gap is more likely in the "discriminative perception / relevance filtering"环节, rather than basic visual recognition.** The "irrelevant chart" experiments in main §4.1 and appendix E.1 (Table 6/12) show that after introducing thematically related but answer-irrelevant charts ('involved' vs 'all'), proprietary models remain essentially unchanged (e.g., Claude-Sonnet-4 on Trend Inference: 70.00→69.11), while open-weight models show significant declines (e.g., InternVL3-78B: 73.21→60.93, approximately 12 points). The original paper summarizes this as "a deficit in discriminative perception: while capable of reasoning with provided data, current open architectures struggle to reject information that is thematically consistent but logically useless." This indicates that the gap is not in "whether a single chart can be understood," but in "whether irrelevant evidence can be filtered out under interference."

**(2) Basic visual recognition (OCR/perception) itself is not the bottleneck; the bottleneck leans more toward the reasoning/instruction-following module.** The cross-lingual experiments in main §4.2 and appendix E.3 provide strong corroborating evidence: models are far more sensitive to changes in **prompt language** than to changes in **chart text language** (e.g., InternVL2-26B drops approximately 8.4 points when the prompt switches from English to Chinese, while chart text switching only changes by approximately 0.9 points). The original paper据此 infers that "visual encoders have robust multilingual OCR and semantic alignment capabilities. The main bottleneck therefore lies in cross-lingual instruction following in the reasoning module." This consistently points with (1) to the conclusion that capability differences arise more from the **reasoning/instruction-following side** rather than the visual encoding side.

**(3) Model scale is indeed one relevant factor, but insufficient to explain the gap alone.** Appendix D.5 observes that smaller-parameter models have performance closer to random selection ("particularly pronounced for smaller-parameter models whose performance approaches random selection"), indicating that scale is positively correlated with discriminative capability. However, main §3.3/§4 also notes that several open-weight models (e.g., Qwen3-VL-32B, InternVL3-78B) already rival proprietary baselines such as GPT-4o in perception and data integration, yet they still lag behind top closed-source models in "noise-resistant filtering"—indicating that **parameter scale alone cannot fully explain the gap**, and factors such as training data/alignment strategies also play a role.

**(4) Our revisions and positioning.** Based on the above, we will: (i) revise the original text to observational descriptions, e.g., "proprietary models exhibit stronger relevance filtering stability under irrelevant chart interference (see §4.1, E.1), and this gap more likely originates from the reasoning/instruction-following环节 rather than basic visual perception (see §4.2, E.3)"; (ii) explicitly acknowledge that existing evidence can only achieve "环节 localization" and **cannot strictly separate the independent contributions of scale / training data / architecture**—this requires controlled experiments with the same architecture but different scales, or the same scale but different training data, which we list as future work to avoid over-attribution. We thank the reviewer for prompting us to state this part more accurately and with clearer boundaries.
